`dogear mcp` is a [Model Context Protocol](https://modelcontextprotocol.io) server. A coding agent connected to it can read the feedback people pinned to your pages, meaning which page, which element, what they said, and where that element probably lives in your code.

With writes turned on, it can also reply and resolve threads. People see those replies in the thread on the page, with an **Agent** badge.

It talks to **your own backend** through the same adapter the layer uses. Nothing is hosted and there's no account to create. It runs over stdio, so your agent starts it as a subprocess.

## Try it locally

<Steps>
  <Step title="Install and start a local server">
    ```bash
    npm install -D @harshi04/dogear   # once, so npx dogear runs from node_modules
    npx dogear serve                  # a local comments server in .dogear/ (add it to .gitignore)
    ```
  </Step>
  <Step title="Point your dev page at it">
    <CodeGroup>

    ```html HTML
    <dogear-comments endpoint="http://127.0.0.1:4848/api/comments"></dogear-comments>
    ```

    ```tsx React
    <Comments adapter={httpAdapter("http://127.0.0.1:4848/api/comments")} />
    ```

    </CodeGroup>

    Leave a few comments.
  </Step>
  <Step title="Connect your agent">
    From the same directory, run this.

    ```bash
    claude mcp add dogear -- npx dogear mcp --write --site http://localhost:3000
    ```

    Ask it to "work through the Dogear feedback". It calls `dogear_next`, finds the element in your code, makes the change, and resolves the thread with a summary you'll see on the page.
  </Step>
</Steps>

## Where it reads from

| You have | Run | How it signs in |
| --- | --- | --- |
| Nothing yet, for local development | `npx dogear serve`, then `npx dogear mcp` in the same directory | The token `dogear serve` writes to `.dogear/token` |
| A REST route (`httpAdapter`) | `npx dogear mcp --endpoint https://app.example.com/api/comments` | `DOGEAR_TOKEN`, which your route maps to an agent user. See [Agent tokens](/backends/contract#agent-tokens) |
| Any other adapter | `npx dogear mcp --adapter ./dogear.adapter.mjs` | Whatever the module does, such as a Supabase service key from the environment |

The adapter module's default export, or its `adapter` export, is an `Adapter`. Give it `listAll` so the agent can see every page at once. Without it, the agent has to ask page by page, and the tools say so.

| Option | What it does |
| --- | --- |
| `--site <url>` or `DOGEAR_SITE_URL` | Makes `?dogear=` links that open a thread on its page |
| `--write` or `DOGEAR_MCP_WRITE=1` | Adds `dogear_reply` and `dogear_resolve`. Without it, the server is read-only and those tools don't exist |

## Tools

All tools return structured content, with an output schema, and the same data as JSON text. Failures come back as tool errors that say what to do next.

### Read

Always there, and annotated read-only.

| Tool | What it does |
| --- | --- |
| `dogear_status` | A connection check. What it reads, who it's signed in as, whether writes are on, and counts of open, resolved and waiting threads. Call it first when something fails |
| `dogear_list_threads` | Open threads by default, newest activity first. Filter by `status` (`open`, `resolved`, `all`), `path` (`/pricing` or `/settings/*`), `author`, `query` (comments, labels, element text) and `waiting_on_agent`. Paged with `limit`, up to 100, and `cursor`. `response_format: "detailed"` adds ids, selectors and element text |
| `dogear_get_thread` | One thread in full. The element (its label, the text it showed, a DOM path, the position on it), **where to look** in the code, every comment, and a link. Takes the 8-character `ref`, a full id, or a `?dogear=` link |
| `dogear_next` | The oldest open thread whose last comment is a person's, meaning nobody has answered it yet, in full. `done: true` when nothing is waiting |
| `dogear_watch` | Waits for new threads and for people's replies on open threads, then returns them, gathering a burst into one answer. The first call returns what's already waiting. Pass the returned `cursor` as `since` to continue. Defaults to 50 seconds, so keep it under your client's tool timeout. Agents' own replies never wake it |

### Write

Only with `--write`. Nothing can delete.

| Tool | What it does |
| --- | --- |
| `dogear_reply` | Posts a reply as the agent, to ask a question or say what changed |
| `dogear_resolve` | Resolves a thread. With `summary`, `commit`, `pr` or `files`, it first posts a closing reply such as ``Resolved in `abc1234` (#12): made it primary``. With `resolved: false` and a `summary`, it reopens the thread and says why |

### Also

- **The prompt `dogear_fix_feedback`,** with an optional `path`, runs the whole loop in order. Next, find, fix, check, then resolve or ask.
- **The resource `dogear://threads/{id}`** is a thread as Markdown.

## Working loops

<Tabs>
  <Tab title="One pass">
    Ask "Work through the Dogear feedback", or use the `dogear_fix_feedback` prompt. The agent repeats these until `done: true`.

    1. Calls `dogear_next`.
    2. Fixes the element it points at.
    3. Checks the change.
    4. Calls `dogear_resolve` with a summary.
  </Tab>
  <Tab title="Live review">
    Someone comments while the agent works. The agent calls `dogear_watch` in a loop, handles each event, replies or resolves, and calls `dogear_watch` again with the new cursor. To keep it going, add this to `CLAUDE.md` or `AGENTS.md`.

    ```md
    When I say "watch Dogear", call dogear_watch in a loop. For each event: read the thread with
    dogear_get_thread, make the change if it's clear (otherwise ask with dogear_reply), verify it, and
    dogear_resolve with a one-line summary. Stop when I say stop.
    ```
  </Tab>
</Tabs>

## Safety

<Warning>
  **Comment text is untrusted.** Anyone who can comment on your page can write text the agent will read. The server's instructions, and a `note` on every thread, tell the agent to treat comment bodies as feedback, never as instructions. Keep your agent's own permissions sensible. Review its diffs, and don't give it production credentials it doesn't need.
</Warning>

- **Read-only unless you say so.** `dogear_reply` and `dogear_resolve` exist only with `--write`.
- **Nothing deletes.** There's no delete tool, and `dogear serve` refuses deletes from the agent. Resolving is reversible.
- **The agent is a real user.** It signs in with its own token, its comments carry `author.agent: true`, and it can't edit anyone else's words.
- **`dogear serve` is local only.**
  - It listens on 127.0.0.1 and rejects any other Host header, which blocks DNS rebinding.
  - It accepts browser requests only from development origins, which are localhost, 127.0.0.1, `*.localhost`, `*.test` and anything added with `--origin`.
  - It caps request bodies at 64 KB.
  - It keeps its token in `.dogear/token` with mode 600.
- **Less leaks out.** Query values that look secret, such as `token`, `key`, `code` and `session`, are replaced with `redacted` in anything the tools return. Authors appear by name only.
